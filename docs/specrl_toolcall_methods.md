# SpecRL 与 Toolcall

## 1. 概述

运行说明：[SpecRL README](specrl/README-specrl.md) · [Toolcall README](toolcall/README-toolcall.md)。实验启动命令见第 4 节。

Agent 在一轮交互中生成工具调用，等待工具返回 observation，再生成下一轮输出。RL 训练还会在 rollout 之后计算 reward、更新 policy 并同步权重。

SpecRL 复用旧 policy 生成的 token，经当前 policy 验证后减少逐 token 解码。
Toolcall 使用历史 observation 提前生成下一轮候选，让生成与真实工具执行重叠。

## 2. SpecRL：验证并复用旧输出

### 2.1 数据与流程

缓存记录旧 rollout 的 draft token IDs、每个 token 的 old logprobs 和 policy version 等元信息。

```text
当前生成请求
  → 查询旧 rollout 缓存
  → 检查 policy version
  → 当前 policy 计算 draft 的 logprobs
  → 确定可接受前缀
      ├─ 全部接受：返回 draft
      ├─ 部分接受：保留前缀，只到不接受处，开始续写
      └─ 验证条件不满足或请求失败：普通生成
```

### 2.2 Token 接受规则

- 旧概率 (q_i)：旧 policy 当初生成它时记录下来，缓存中保存的是 old_logp_i = log(q_i)。
- 新概率 (p_i)：把 prompt + draft 输入当前 policy，让模型在相同前缀下重新评估这个 token，得到 new_logp_i = log(p_i)。这相当于给已有答案逐 token 打分，不需要重新逐个生成。

对第 `i` 个 draft token，当前实现判断：

```text
log(max(U_i, 1e-12)) <= new_logp_i - old_logp_i + bias
U_i ~ Uniform(0, 1)
```

这条公式按新旧概率比决定是否接受 token。条件等价于：

```text
log(U_i) <= log(p_i / q_i) + bias
U_i <= exp(bias) * p_i / q_i
```

`U_i` 在 0 到 1 之间均匀取值，因此接受概率为：

```text
alpha_i = min(1, exp(bias) * p_i / q_i)
```

`bias=0` 时，若新 policy 给该 token 的概率不低于旧 policy，则必然接受；概率下降时，按 `p_i/q_i` 的比例接受。

正 bias 放宽接受，负 bias 收紧接受。使用 log 形式可以直接计算模型返回的 logprobs，避免先还原很小的概率再做除法。

本文 Demo、3090/1.7B 和 A100/8B 实验均使用 `bias=0.5`，接受概率为 `min(1, 1.6487*p_i/q_i)`；新概率达到旧概率约 60.65% 时，该 token 即必然接受。

### 2.3 演示 Demo

本次 Demo 用一组短程配对运行，展示 SpecRL 从缓存填充、跨版本验证到复用输出的完整过程，并通过分阶段计时观察加速来自哪里。

**实验设计**

| 项目 | 设置 |
| --- | --- |
| 模型与部署 | Qwen3-1.7B；两组双卡分别部署一个 TP=2 副本 |
| 对照方式 | Baseline 与 SpecRL 各运行一次，保持相同模型、输入与生成长度配置 |
| 生成工作量 | 每个 prompt 生成 4 条 rollout，每条输出固定为 2,048 tokens |
| 运行步数 | 6 steps；第 1 步预热，steps 2–6 统计稳态性能 |
| 稳态 token 核对 | 两边均为 213,700 prompt tokens + 40,960 response tokens，共 254,660 tokens |
| 性能负载 | Reward、loss、grad 均为 0，观察高接受率条件下的执行耗时 |

**执行过程**

1. 第 1 步的 4 次缓存查询均为冷启动 miss，完成普通生成后写入 draft tokens、old logprobs 和 policy version。
2. 后续 5 步共进行 20 次查询，全部命中缓存；版本检查决定使用验证路径还是普通生成。
3. 10 次跨版本路由进入 verification，共验证 20,480 个 draft tokens，全部接受，直接复用完整输出。
4. 另外 10 次为 equal-policy 路由，正常生成，保留同一 policy下的 rollout 多样性。

**耗时与收益分析**

| 计时范围 | Baseline | SpecRL | 节省时间 | 加速比 |
| --- | ---: | ---: | ---: | ---: |
| 端到端 | 803.131 s | 711.349 s | 91.782 s | **1.129×** |
| 稳态 Trainer | 444.960 s | 399.139 s | 45.821 s | **1.115×** |
| 稳态 Rollout | 270.286 s | 226.232 s | 44.054 s | **1.195×** |
| 稳态 Actor update | 155.665 s | 154.092 s | 1.573 s | 1.010× |

Rollout 耗时下降 **16.3%**，其节省的 44.054 s 占 Trainer 总节省的 **96.1%**。Actor update 基本保持相同耗时，说明本次 Trainer 提速主要来自生成阶段。

从内部计时看，稳态缓存查询合计 0.059 s、版本检查合计 0.141 s，10 条 draft 的验证合计 33.058 s，平均约 **3.306 s/条**；同版本普通生成路径平均约 **23.443 s/条**。
可以看到批量验证已有 tokens 相对于逐 token 生成的成本差异。

### 2.4 实验结果

分别在 **Qwen3-1.7B / 8×RTX 3090** 与 **SWE-Lego-Qwen3-8B / 8×A100** 上进行，比较生成阶段的收益及其对完整训练循环的影响。

**实验设计**

两组配置各运行 5 组 Baseline/SpecRL 配对，每次 30 steps，前 5 步预热，后 25 步统计稳态性能。配对使用相同模型、数据、seed 和训练配置，固定输出长度为 2,048 tokens，并交替执行顺序。每次稳态处理的工作量均为 **1,272,900 tokens**，其中 prompt 为 1,068,100、response 为 204,800。

以下结果为 5 次运行的平均值。端到端耗时覆盖启动及全部训练步骤；Trainer、Rollout 为预热后的累计耗时。实验采用零有效 policy 更新、高接受率的固定长度性能负载。

| 配置 | 指标 | Baseline | SpecRL | 耗时下降 | 加速比 |
| --- | --- | ---: | ---: | ---: | ---: |
| 1.7B / 3090 | Rollout | 1,247.794 s | 1,101.231 s | 11.75% | **1.133×** |
| 1.7B / 3090 | Trainer | 1,885.940 s | 1,727.334 s | 8.41% | **1.092×** |
| 1.7B / 3090 | 端到端 | 2,506.154 s | 2,324.214 s | 7.26% | **1.078×** |
| 8B / A100 | Rollout | 1,971.611 s | 1,092.458 s | 44.59% | **1.805×** |
| 8B / A100 | Trainer | 5,262.879 s | 4,348.379 s | 17.38% | **1.210×** |
| 8B / A100 | 端到端 | 6,875.704 s | 5,825.768 s | 15.27% | **1.180×** |

**1.7B / 3090**

Rollout 平均节省 **146.563 s**，占 Trainer 节省 158.606 s 的约 **92.4%**。Actor update 仅下降 2.18%，old logprob 与权重同步耗时接近，主要变化集中在生成阶段。5 组配对的端到端时间均下降，平均每次完整运行节省 **181.940 s**。

稳态草稿接受率为 **99.94%**，复用 token 占总输出的 **58.56%**。这说明一旦进入验证路径，绝大部分草稿可被复用；整体收益还取决于跨版本验证覆盖了多少 rollout。

**8B / A100**

稳态验证覆盖全部 100 次缓存命中，每次运行的 **204,800 个 draft tokens 全部接受**，输出覆盖率为 **100%**。验证阶段平均累计约 902.058 s，缓存查询与版本检查合计约 3.445 s；主要生成工作转为对已有 draft 的验证。

Rollout 平均节省 **879.153 s**，占 Trainer 节省 914.500 s 的约 **96.1%**。这部分收益将 Trainer 加速到 **1.210×**，并带来 **1.180×** 端到端加速；5 组配对均有收益，每次完整运行平均节省 **1,049.936 s，约 17.5 分钟**。

两组结果共同体现了 SpecRL 的收益链路：**复用通过验证的 tokens → 缩短 Rollout → 缩短 Trainer → 减少端到端时间**。8B/A100 配置同时具有更高的验证覆盖率；两组模型、硬件和路由覆盖率均有差异，因此分别报告各自配置下的实测结果。

## 3. Toolcall：提前生成下一轮候选

### 3.1 为什么能并行

假设 Agent 再次调用一个工具，缓存中已有该操作的历史成功 observation。系统可以先把历史 observation 当作预测输入，生成下一轮候选，同时执行当前真实工具。工具返回后，再判断候选是否适用于真实上下文。

```text
Baseline
当前 action → 真实工具 → observation → 下一轮生成

Toolcall
当前 action → 命中历史 observation
              ├─ 构造预测消息 → 候选生成 ─┐
              └─ 执行真实工具 → 真实结果 ─┴─ 校验 → 提交或丢弃
```

候选生成只调用模型，不提前执行候选中的工具。真实工具依旧执行一次。

### 3.2 Observation 缓存

缓存 key 包含规范化后的工具调用信息和 schema 签名，附带的参数用 JSON 表示。

另外也实现了支持等价调用，例如 `bash` 与 `execute_bash` 这些命令，以及部分只读文件操作。等价命中提供预测 observation，但是仍然需要执行真实工具验证后才可以接受。

缓存只保存 `status=ok` 的结果，使用 entry/token 双上限 LRU；采用上限为 1,024 条和 1,000,000 个 tokens。

### 3.3 提交条件与后续执行

提交需要同时满足：

- 预测 tool message 与真实 tool message 编码后的 token IDs 一致。
- 候选完整 context 与正式上下文一致。
- Policy version、sampling signature 和 tool schema signature 一致。
- 真实工具成功、session 有效，且未进入终止状态。

校验通过后，候选保存为 `pending_generation`，下一轮使用并清空，从而省去一次正常生成。校验失败则丢弃候选，只把真实 observation 加入正式上下文，下一轮正常生成。真实结果匹配但候选尚未完成时，当前实现最多等待 30 秒；不匹配时发起取消。取消操作异步处理，正式交互可继续推进。

### 3.4 时间模型

缓存命中且候选成功提交时，简化模型为：

```text
T_baseline ≈ T_tool + T_model
T_toolcall ≈ max(T_tool, T_model) + T_lookup/encode/validate
```

忽略开销时，局部理想加速比最高为 2，且在工具耗时与生成耗时接近时收益最大。整条轨迹还受到命中率、提交率、首次填充、工具超时、候选浪费和固定开销影响。

### 3.5 实验结果

选取两组代表实验：0.5 秒固定工具对照用于观察并行收益，真实 SWE 任务用于展示完整交互中的候选生成、验证与复用。

#### 3.5.1 控制 0.5 秒工具：完整轨迹加速 1.303×

**实验设计**

工具固定执行以下命令，保持等待时长和 observation 内容一致：

```bash
sleep 0.5 && printf 'TOOLCALL_BENCH_OK\n'
```

Baseline 串行执行工具与下一轮生成；Toolcall 在历史 observation 命中后并行启动候选，真实结果匹配后直接采用。两种模式共运行 3 组配对，每条实际轨迹均完成 **8 次该工具调用、423 个输出 tokens**，prompt、response、action、observation 和退出状态逐项一致。

首次调用完成缓存填充，后续 7 次均启动候选并成功提交。三组 Toolcall 的候选统计均为 **7 次启动、7 次提交、0 次丢弃**；提交时候选已完成，无需额外等待。

**配对结果**

下表统计轨迹内各交互步骤的累计耗时，对应报告的 `prefix_wall_s`。由于三组配对均全程匹配，这里的匹配前缀覆盖完整实际轨迹。

| 配对 | Baseline | Toolcall | 加速比 |
| --- | ---: | ---: | ---: |
| 1 | 13.772 s | 10.686 s | 1.289× |
| 2 | 13.967 s | 10.480 s | 1.333× |
| 3 | 13.942 s | 10.822 s | 1.288× |
| 平均耗时 | **13.894 s** | **10.663 s** | **1.303×** |

完整实际轨迹平均节省 **3.231 s**，耗时减少约 **23.3%**。三组记录的重叠时间分别为 3.793、3.792、3.795 s，与连续 7 次复用工具等待窗口的过程一致。

以其中的 Step 3 为例：

| 指标 | Baseline | Toolcall |
| --- | ---: | ---: |
| 真实工具执行 | 约 0.542 s | 约 0.543 s |
| 单步总耗时 | 1.050706 s | 0.545815 s |
| 单步加速比 | — | **1.925×** |

Baseline 中约 0.507 s 的生成与约 0.542 s 的工具执行串行发生；Toolcall 将候选生成放入工具执行窗口，单步耗时接近两者中较长的一段。因此，收益来自**生成与工具执行的重叠**，而非模型解码吞吐提升。

#### 3.5.2 真实 SWE-bench

**实验设计**

使用 SWE-Lego-Qwen3-8B，在 `astropy__astropy-12907` 上运行一组 Baseline/Toolcall 对照。两边使用相同 seed 和确定性生成配置，均记录 100 轮、100 次 action，并以 `max_step_limit` 结束。Agent 在真实环境中读取源码、执行检查、修改文件，并根据 observation 继续推理。

**候选执行分析**

Toolcall 共启动 **8 次候选**，其中 **2 次通过验证并提交**，**6 次根据真实 observation 重新生成**；归档记录的隐藏工具时间合计约 **0.803 s**。两次提交在 Step 65、74 标记为 `generation_source="candidate"`，日志同时记录 `Consumed committed speculative candidate`。

代表案例是 Step 64 → 65：Agent 再次执行 `python final_verification.py`，命中此前 Step 35 的 observation。真实工具返回与预测内容一致，校验通过后保存候选，Step 65 直接消费该结果。对应工具执行窗口为 **0.735 s**。

这个过程展示了真实任务中的完整链路：**重复工具调用 → 历史 observation 命中 → 候选与工具并行 → 真实结果验证 → 下一轮直接复用**。源码修改导致工具输出变化时，系统采用真实 observation 继续生成，保持后续交互与当前环境一致。

## 4. 后续改进方向

### 4.1 SpecRL

1. **开展多 turn 测试** 在真实 SWE-bench 任务中，将 Agent 交互轮数上限设置为 100，开展 Baseline 与 SpecRL 配对实验，允许任务完成后提前结束。重点观察长程交互中的生成耗时、端到端加速比、输出复用情况和任务完成效果，据此确定后续优化重点。
2. **评估实际训练中的收益** 在包含有效策略更新的训练过程中，观察不同训练阶段的复用效果，以及加速对训练效率和任务表现的影响，明确适合使用 SpecRL 的场景。

### 4.2 Toolcall

1. **测试实际 reward 表现** 在 SWE-bench 任务上开展实验，结合任务完成效果和端到端耗时，分析不同工具类型、调用频率与等待时长下的加速收益和方法表现。
2. **提高复用比例** 围绕重复操作和稳定输出等，优化历史结果的组织与使用方式，让更多工具调用能够转化为实际节省的等待时间。
